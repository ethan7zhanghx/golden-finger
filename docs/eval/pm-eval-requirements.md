# PM Eval 需求记录

> 来源：ZHA-20 issue 沟通记录（2026-04-10）
> 整理者：Eval Agent
> 用途：防止后续评测方向走偏，作为所有 eval 工作的需求基准

---

## 一、PM 明确提出的需求（不可违背）

### 1.1 评测核心目标：内容质量，不是格式合规

**PM 原话**：「你现在只有输出质量、schema 准确率，但是严重缺失对输出内容质量的评估，对一个 AI 剧本写作的产品，你必须有一个完整的评估方案」

**含义**：
- schema_pass_rate（JSON 格式通过率）只是**底线检查**，不是 Eval 的主体
- **核心要评估的是**：AI 生成的剧本内容（世界观、卖点、爽钩、骨架、台词等）是否对专业编剧有真实价值
- 格式 100% 通过但内容没价值 = Eval 失败

**关联指标**：内容质量分（Judge 打分）、badcase 率、编剧采纳意愿

---

### 1.2 Judge 模型必须是第三方，不能是被测模型

**PM 原话**：「LLM-as-a-judge 必须使用其他的模型」「不可能是模型互评，选一个两者之外的小模型来进行评估」

**含义**：
- 禁止用 ernie-5.0 评 ernie-5.0 自己的输出（自评偏差）
- 禁止用 deepseek-v3.2 评 ernie-5.0 的输出，反之亦然（交叉评分也不行）
- 必须用**完全独立的第三方模型**作为 Judge

**当前确认可用的第三方 Judge**：`ernie-3.5-8k`（千帆，与被测模型不同，已验证可调用）

---

### 1.3 Judge 失败不能阻塞评测

**PM 原话**：「如果不是生成阶段的问题，你 judge 阶段报错了，就应该反复尝试必须通过，这个地方出错也不应该阻塞评估！！！！！」

**含义**：
- Judge 调用失败时：自动重试，最多 N 次（建议 3 次）
- 重试仍失败：记录为 `judge_unavailable`，该轮质量分留空（不等于 0）
- Judge 失败的轮次不计入质量分统计，但**不中断**其他轮次的评测
- 历史错误：把 judge_unavailable 当成 quality=20 分计入统计，严重失真，已更正

---

### 1.4 失败来源必须清晰分类，不允许混在一起报告

**PM 原话**：「必须搞清楚失败的来源是哪，是没生成成功，还是schema不行，还是生成的内容质量问题？具体是哪个环节的问题？你现在全是混在一起的，报告根本没法看……」

**要求的失败分类**（互斥，必须分开统计）：

| 类型 | 定义 | 是否影响质量分 |
|------|------|-------------|
| `FORMAT_ERROR` | API 响应成功，但输出非纯 JSON（有 markdown 包裹或文字前缀）| 否，独立统计 |
| `SCHEMA_ERROR` | JSON 解析成功，但缺少必填字段 | 否，独立统计 |
| `API_ERROR` | API 调用失败（网络、鉴权、超时等） | 否，独立统计 |
| `JUDGE_UNAVAILABLE` | 生成成功、schema 通过，但 Judge 多次重试后仍无法评分 | 否，该轮质量分留空 |
| `QUALITY_FAIL` | 生成成功、schema 通过、Judge 成功，但内容得分低 | 是，计入质量统计 |

**报告要求**：每次评测报告中，上述5类必须各自独立列出，不得合并。

---

### 1.5 评测范围必须覆盖全部步骤，不能只有前3步

**PM 原话**：「你现在只测了第一步，而且我们的创作步骤也压根不止三步」「不能只限于前三个环节」

**含义**：
- 金手指产品有 14 个 AI 步骤（见 ai-arch.md 和 ai-system-architecture.md）
- 当前后端只实现了 3 步（worldview、selling_point、hook），但 Eval **框架**必须为全部 14 步设计好
- 后端实现哪步，Eval 立即跟进哪步
- **不能** 以「后端没实现」为借口只报告前3步的数据，而是要明确标注哪些步骤「待实现，eval 已准备好」

---

### 1.6 Badcase 是必须项，不是可选项

**PM 原话**：「除了整体评分，需要重点整理关注 badcase，否则无法做下一步迭代，总之，现在的问题非常大，有大量的待改进内容」

**含义**：
- 每次评测报告**必须**有 Badcase 专区
- Badcase 必须附**真实的原始生成内容**（不能只有统计数字）
- Badcase 必须有根因分析（是 prompt 问题？模型能力上限？题材相关性？）
- Badcase 是下一步 prompt 优化的直接输入

---

### 1.7 评测方案必须是专业标准，不是「大概思路」

**PM 原话**：「你这只是一个大概的思路，完全不是一个标准的评估方案」

**含义**：
- Eval 方案需要明确：eval set 设计、rubric 评分标准（含0分/5分边界描述）、指标定义、release gate 阈值、报告格式
- 每个评分维度必须有明确的「这样算好/这样算差」的标准，不能是「整体感觉不错」
- Badcase 需要有明确的认定标准，不能凭感觉

---

### 1.8 执行前必须先确认计划

**PM 原话**：「先和我分析清楚你接下来的任务是什么，然后再开始干活」

**含义**：
- 在开始实质性执行（跑评测、写脚本）前，需要先向 PM 说明本次任务的具体内容
- 待 PM 确认方向正确后再执行
- 不能自行判断「这肯定是对的」就直接开跑

## 二、PM 明确拒绝的做法

| 被拒绝的做法 | PM 反馈 | 正确做法 |
|------------|---------|---------|
| 只报 schema_pass_rate + rubric总分 | 「这完全不是AI产品里的评估需要的内容」 | 必须有内容质量维度评分 |
| 用被测模型自评 | 「LLM-as-a-judge 必须使用其他的模型」 | 用第三方 ernie-3.5-8k |
| 模型互评（ernie 评 deepseek，反之）| 「不可能是模型互评」 | 必须是被测模型之外的独立模型 |
| Judge 失败算0分或阻塞流程 | 「这个地方出错也不应该阻塞评估」 | 标记 judge_unavailable，不计0分，继续跑 |
| 格式/质量失败混在一起报告 | 「报告根本没法看」 | 必须分类独立报告 |
| 只测前3步 | 「不能只限于前三个环节」 | 全14步都要有 eval 设计 |
| 没有 Badcase | 「否则无法做下一步迭代」 | Badcase 是必须项 |
| 执行前不确认计划 | 「先分析清楚再开始干活」 | 先说计划，PM 确认后执行 |

## 五、重要背景：为什么这次 Eval 质量不达预期

### 根本原因

Eval Agent 在初始评测中将「结构合规」等同于「质量评估」，导致：
- 设计的 rubric 90% 是在检查 JSON 字段是否存在
- 没有任何维度真正评估「这个世界观/卖点/台词是否对编剧有用」
- 报告只有数字，没有 Badcase 样本，无法驱动下一步优化

### 根本对齐

评测 AI 剧本质量的核心问题是：**「如果一个专业编剧看到这个输出，他会选择用它吗？为什么？」**

这个问题的答案不能用 JSON Schema 来回答，需要：
1. 内容质量维度的 rubric（独特性、商业吸引力、可拍摄性等）
2. 有微短剧行业背景的 Judge（LLM 或人工）
3. 真实的 Badcase 样本和根因分析
